# SDD 开发 Session：内容提纲与逐页规划

> 状态：内容规划稿，不是演示稿实现。  
> 目标：先确定“讲什么、为什么这样讲、每页不讲什么”，通过评审后再统一修改 `slides.md`。  
> 页数：40 页（封面 1 页 + 内容 39 页），不设置独立的章节过场页，不包含 Session 组织、议程说明或 Workshop 安排。

## 1. 内容主线

整场分享只回答一个核心问题：

> 当 AI 从“代码补全工具”变成“可以连续执行任务的 Agent”后，团队如何把模糊意图稳定地转化为可验收的软件？

叙事采用八段递进：

1. **开发方式为什么必须改变**：从无 AI、早期 AI、Agent，一直走到 Harness 和工程方法论。
2. **SDD 提供什么控制面**：先建立 SDD 的整体模型，再进入三个核心环节。
3. **Spec**：定义要实现的真实意图、边界和证据。
4. **Plan**：把 Spec 转换成依赖清晰、可验证的执行图。
5. **Implement**：用 TDD、Loop、Verify 与 Reconcile 让实现持续收敛。
6. **框架与工具**：方法讲完之后，再介绍 Grill、OpenSpec、Spec Kit、Superpowers 如何固化方法。
7. **可复用能力工程**：通过分级知识库、Plugin、Marketplace、Harness、Eval 把项目经验变成组织能力。
8. **团队规模化**：讨论风险、反例、分工、落地路线和度量，最后形成完整系统图。

## 3. 逐页内容规划

### 00｜封面：从意图到可靠交付

- **核心结论**：SDD 不是“多写一份文档”，而是让人和 Agent 围绕同一套可执行意图协作。
- **页面内容**：主标题“Spec-Driven Development”；副标题“从意图到可靠交付”；一句引导问题“Agent 会写代码以后，团队还需要设计什么？”
- **讲述重点**：把听众注意力从具体 AI 工具转向交付系统。
- **不要放**：完整议程、演讲人长简介、工具 Logo 墙。

## 一、AI 开发方式的演进

### 01｜没有 AI：人驱动完整开发链

- **核心结论**：传统开发的主要约束是人的实现带宽，因此流程围绕分工、评审和交接设计。
- **页面内容**：需求理解 → 方案设计 → 任务拆分 → 编码 → 测试 → Review → 发布；每个阶段标出主要责任人和产物。
- **讲述重点**：人既负责决策，也负责大部分执行；代码是最昂贵的产物之一。
- **不要放**：对传统开发的贬低，或把瀑布、敏捷混为一谈。

### 02｜早期 AI：代码更快，角色没变

- **核心结论**：补全、问答和代码片段提高了局部速度，但任务分解、上下文管理与验证仍由人承担。
- **页面内容**：在传统开发链的“编码”环节叠加 Copilot/Chat 式能力；列出补全、解释、生成测试、局部重构四类帮助。
- **讲述重点**：局部效率提升没有改变系统边界，甚至会把瓶颈推向 Review 和验证。
- **不要放**：具体模型排行榜或厂商比较。

### 03｜Agent：从回答问题到完成任务

- **核心结论**：Agent 能观察环境、使用工具、修改文件、运行验证并迭代，但不能替团队决定含糊的业务意图。
- **页面内容**：Agent 执行环“理解 → 计划 → 行动 → 观察 → 修复”；外圈展示读代码、写代码、搜索、调用工具、运行测试、提交结果等能力；边界区分“事实可调查”与“选择需确认”。
- **讲述重点**：自主执行能力变强后，输入质量和控制机制的重要性同步上升。
- **不要放**：“Agent 可以完全替代工程师”的结论。

### 04｜Agent 能力栈：能力不只来自模型

- **核心结论**：可靠性来自模型之外的上下文、规则、技能、工具、记忆与协作机制。
- **页面内容**：Model、Context、Rules、Skills、Tools、MCP、Memory、Sub-agent 八层；每层只给一个职责说明。
- **讲述重点**：Skill 是可复用做法，MCP/Tool 是可调用能力，Memory/Knowledge 是持续上下文，它们不应混称。
- **不要放**：每个概念的产品清单，避免这一页变成术语百科。

### 05｜Harness：把 Agent 放进工程系统

- **核心结论**：Harness 是 Agent 的运行与控制系统，负责组装上下文、约束动作、管理循环、收集证据并在必要时升级给人。
- **页面内容**：中心是 Agent，外部控制面包括 Context Assembly、Permission、Workflow、State、Verification、Observability、Human Escalation。
- **讲述重点**：同一模型在不同 Harness 中会表现出完全不同的工程可靠性。
- **不要放**：把 Harness 等同于 IDE 或单个 CLI。

### 06｜方法论演进：从生成代码到设计系统

- **核心结论**：方法论的演进是在逐步解决“意图、上下文、验证和复杂依赖”四类失控问题。
- **页面内容**：Vibe Coding → Prompt Engineering → Context Engineering → SDD → Loop Engineering → Graph Engineering；每一阶段只标出新增控制能力。
- **讲述重点**：这些概念不是严格替代关系，而是层层叠加的工程能力。
- **不要放**：人为制造单一、线性的行业历史结论。

## 二、进入 SDD

### 07｜AI 改变了瓶颈

- **核心结论**：代码生成成本下降后，瓶颈从“怎么写”迁移到“写什么、边界是什么、如何证明做对了”。
- **页面内容**：Before/After 对比；Before 突出实现带宽，After 突出意图澄清、系统约束和验证证据。
- **讲述重点**：SDD 首先解决的是控制与沟通问题，其次才是效率问题。
- **不要放**：未经来源支持的生产率百分比。

### 08｜SDD 用 Spec 建立共享执行协议

- **核心结论**：SDD 以 Spec 为事实源，让人、Agent、测试和评审围绕同一份可验证契约协作。
- **页面内容**：Intent（为什么/为谁）、Contract（行为/边界）、Evidence（如何证明）三部分；四类参与者围绕 Spec 排布。
- **讲述重点**：Spec 不是静态需求文档，而是持续驱动计划、实现与验证的协议。
- **不要放**：把 SDD 定义成“先写文档再写代码”。

### 09｜SDD 的主路径与完整闭环

- **核心结论**：核心主路径是 Spec → Plan → Implement，可靠交付还需要 Explore、Clarify、Verify 与 Reconcile 形成外部闭环。
- **页面内容**：中心三阶段；外环为 Explore → Clarify → Spec → Plan → Implement → Verify → Reconcile → Spec。
- **讲述重点**：后三章先脱离工具，把三个核心环节讲清楚。
- **不要放**：OpenSpec、Spec Kit 或 Superpowers 的命令名。

## 三、Spec：定义正确的问题

### 10｜Spec 固定行为契约，不预设实现路径

- **核心结论**：Spec 是对可观察行为与决策边界的契约，不是愿望清单、实现教程或一次性文档。
- **页面内容**：左右等宽对照错误输入与执行协议；四行分别展开共享事实、行为契约、边界声明与验收依据，底部汇总 What、Why、Constraints 与 Evidence。
- **讲述重点**：Spec 主要回答 What、Why、Constraints 与 Evidence，把 How 留给 Plan。
- **不要放**：过多模板字段。

### 11｜可执行 Spec 的组成

- **核心结论**：好的 Spec 必须把目标、行为、边界和验收同时写清楚。
- **页面内容**：背景与问题、目标/非目标、用户与场景、业务规则、接口/数据契约、异常与边界、非功能约束、验收标准八块；用一个贯穿示例说明字段如何互相约束。
- **讲述重点**：非目标和边界情况与正向需求同等重要。
- **不要放**：完整的大型模板全文。

### 12｜好 Spec 的六个质量维度

- **核心结论**：Spec 质量可以被检查，而不是凭“看起来很详细”判断。
- **页面内容**：Clear、Complete、Consistent、Verifiable、Traceable、Evolvable；每项对应一个检查问题。
- **讲述重点**：详细不等于清晰；真正的质量来自减少多种合理解释。
- **不要放**：把字数或文档页数当质量指标。

### 13｜Spec 评审门：进入 Plan 前先消除歧义

- **核心结论**：未消除的歧义会在 Agent 执行中被放大，因此必须在进入 Plan 前显式审查。
- **页面内容**：歧义、边界、证据、隐含决策、非目标五项 Gate；一个 Bad → Better 微型示例；结尾给出通过条件。
- **讲述重点**：可从环境查到的事实由 Agent 调查，真正的产品/架构选择由人确认。
- **不要放**：把所有未知项都强迫用户回答。

## 四、Plan：设计可执行路径

### 14｜Plan 把 Spec 转换成可验证的执行路径

- **核心结论**：Plan 是从 Spec 到可验证改动的执行设计，不是把需求重新换一种说法，也不是按文件罗列 Todo。
- **页面内容**：Plan 应包含架构落点、任务边界、依赖、风险、测试策略、验证命令；反面是大步任务、无依赖顺序、只有改动列表、没有完成证据。
- **讲述重点**：Plan 负责 How，但每一个 How 都必须追溯到 Spec。
- **不要放**：具体框架生成的 `plan.md` 截图。

### 15｜好 Plan = 任务节点 + 依赖关系 + 质量门

- **核心结论**：一份可执行 Plan 需要清晰任务节点、真实依赖边和可判定质量门。
- **页面内容**：Node 包含目标、输入、输出、文件范围、验证；Edge 表示数据/接口/顺序依赖；Gate 表示测试、Review、验收和风险控制。
- **讲述重点**：小任务不是目的，降低耦合并让失败可定位才是目的。
- **不要放**：机械地规定每个任务固定分钟数。

### 16｜Graph Engineering：让复杂工作可并行、可恢复

- **核心结论**：当任务存在依赖、并行、反馈和失败恢复时，Plan 应被视为图，而不是线性清单。
- **页面内容**：示例 DAG：契约/Schema → 后端与前端并行 → 集成 → 验收；标出关键路径、并行节点、Gate、失败回退和汇合点。
- **讲述重点**：图既服务多人协作，也服务多个 Agent 或 Sub-agent 的调度。
- **不要放**：把任意待办列表包装成“Graph Engineering”。

## 五、Implement：让实现持续收敛

### 17｜可信交付必须同时包含改动与证据

- **核心结论**：Implement 是围绕 Spec 和 Plan 生成证据、持续收敛的过程，不是一次性生成大量代码。
- **页面内容**：从任务节点到代码、测试、日志、Review 证据，再回到验收项；反面列出“大爆炸式改动、跳过验证、顺手扩范围、完成即宣称正确”。
- **讲述重点**：实现阶段最小的可信单位不是代码 diff，而是“改动 + 验证证据”。
- **不要放**：单纯展示 Agent 写代码的录屏或炫技 Demo。

### 18｜TDD：把验收条件变成快速反馈

- **核心结论**：Red → Green → Refactor 把 Spec 的行为要求转成可重复证据，并限制 Agent 在错误方向上扩张。
- **页面内容**：Acceptance Criterion → Failing Test → Minimal Implementation → Passing Test → Refactor；强调先看到“正确失败”。
- **讲述重点**：TDD 不等于追求覆盖率，而是在实现前固定可观察行为。
- **不要放**：只讲单元测试；应包含适合该行为层级的集成或端到端测试。

### 19｜Loop Engineering：设计可控的执行循环

- **核心结论**：Agent 的价值来自循环，可靠性来自循环的观察、验证、预算和退出条件。
- **页面内容**：Act → Observe → Verify → Repair；外部 Guardrails 包含 scope、permission、budget、retry、timeout、escalation、stop condition。
- **讲述重点**：没有退出条件的循环不是自主，是失控。
- **不要放**：把“多试几次”当作 Loop Engineering。

### 20｜验证与对账：做完不等于做对

- **核心结论**：Verify 判断实现是否满足 Spec，Reconcile 处理实现与规格之间的新事实和偏差。
- **页面内容**：Verify 检查测试、静态检查、行为验收、非功能约束、人工 Review；Reconcile 有三种结果：修实现、修 Plan、经批准后修 Spec。
- **讲述重点**：代码不能静默反向定义需求；Spec 变化必须成为显式决策。
- **不要放**：把测试通过当成唯一完成条件。

## 六、框架与澄清工具

### 21｜框架的作用：把方法变成可重复机制

- **核心结论**：方法论说明“应该怎样做”，框架把它固化成 Artifact、Command、Workflow、Gate 和 State。
- **页面内容**：Methodology → Framework → Harness 三层；分别对应原则、流程资产、运行控制。
- **讲述重点**：先有团队需要解决的问题，再选择框架；框架不能代替方法理解。
- **不要放**：马上给出工具排名。

### 22｜Grill：先把当前决策前沿问清楚

- **核心结论**：Grill 用依赖化的决策树逐层澄清问题，只提当前可回答的问题，并区分事实调查与人类选择。
- **页面内容**：Decision Tree、当前 Frontier、回答后暴露下一层；Loose Idea → Confirmed Decisions。
- **讲述重点**：它提高的是 Spec 的输入质量，不是替代 Spec。
- **不要放**：把 Grill 理解成一次抛出几十个问题的问卷。

### 23｜Grill 能力族：根据问题规模选择澄清方式

- **核心结论**：不同入口解决不同的澄清半径，但共享“先调查事实、再确认决策”的原则。
- **页面内容**：`grill-me`（轻量、无状态）、`grill-with-docs`（同步 CONTEXT/ADR）、`to-questionnaire`（交给领域专家异步回答）、`wayfinder`（大型问题的 Issue/Decision Graph）。
- **讲述重点**：展示从单次对话到组织知识沉淀的连续谱。
- **不要放**：逐条演示 Skill 的安装和命令。

### 24｜OpenSpec：围绕 Change 管理规格演进

- **核心结论**：OpenSpec 擅长管理一次变更的 Artifact 依赖、Delta Spec、同步与归档。
- **页面内容**：Explore → Proposal → Specs + Design → Tasks → Apply → Verify → Sync → Archive；突出 Change、Artifact DAG、主规格与历史。
- **讲述重点**：它解决“规格如何随变更持续演进”。
- **不要放**：把 OpenSpec 描述成完整的 Agent 执行纪律框架。

### 25｜GitHub Spec Kit：标准化 SDD 产物链

- **核心结论**：Spec Kit 用 Constitution、阶段化产物和质量 Gate 将意图稳定地转换为任务与实现。
- **页面内容**：Constitution → Specify → Clarify → Plan → Checklist → Tasks → Analyze → Implement → Converge；突出每个阶段的产物。
- **讲述重点**：它解决“团队如何形成一致的 SDD 工作流与交付物”。
- **不要放**：把 Checklist 当成验收测试；它首先检查需求文本质量。

### 26｜Superpowers：把执行纪律装进 Agent

- **核心结论**：Superpowers 通过可组合 Skill 和强制触发规则，让 Agent 遵循澄清、批准、计划、TDD、Review 与收尾流程。
- **页面内容**：Brainstorm → Approve → Plan → Worktree → Execute/Sub-agent → TDD → Review → Finish。
- **讲述重点**：它更偏执行纪律与工程闭环，不只是规格文件管理。
- **不要放**：暗示必须使用 Sub-agent 才算 SDD。

### 27｜框架选择与组合：按缺口选，不按热度选

- **核心结论**：OpenSpec、Spec Kit、Superpowers 解决的主问题不同；组合时必须只有一份权威 Spec、一份任务状态和一套完成标准。
- **页面内容**：比较规格演进、标准产物、执行纪律、澄清、验证五个维度；给出三种典型选择场景；列出组合红线。
- **讲述重点**：避免三套框架同时生成互相竞争的 Plan/Tasks。
- **不要放**：给出脱离团队上下文的“最佳框架”。

## 七、可复用能力工程

### 28｜从项目资产到组织能力系统

- **核心结论**：可复用能力不是一个提示词文件夹，而是知识、插件、分发、运行和评估组成的系统。
- **页面内容**：Tiered Knowledge → Plugin → Marketplace → Harness → Eval/Telemetry；下方展示项目反馈如何回流。
- **讲述重点**：知识回答“知道什么”，Plugin 回答“如何封装”，Marketplace 回答“如何发现与治理”，Harness 回答“如何运行”。
- **不要放**：直接进入目录结构细节。

### 29｜分级知识库：按稳定性和作用域组织上下文

- **核心结论**：知识应按稳定性、权威性和作用域分层，运行时向下组装，复盘时向上晋升。
- **页面内容**：L0 通用原则；L1 组织治理/工程标准；L2 领域、平台、仓库架构与 ADR；L3 项目/Feature 的 Spec、Plan、Runbook；L4 任务会话、日志和临时证据。
- **讲述重点**：高层越稳定、越精炼；低层越具体、越易过期。重复出现的 L4 经验经评审后才能上升。
- **不要放**：把所有文档无差别塞进向量库。

### 30｜Plugin：可版本化、可测试的能力发布单元

- **核心结论**：Plugin 将知识与行动机制封装成可安装、可升级、可回滚的发布单元。
- **页面内容**：Manifest、Knowledge、Rules、Skills、Tools/MCP、Templates、Workflows、Evals、Examples；标注依赖、权限、版本和 Owner。
- **讲述重点**：Skill 是 Plugin 内的一种能力，不等于完整 Plugin。
- **不要放**：把 Plugin 只定义成第三方工具连接器。

### 31｜Plugin Marketplace：让能力可发现、可治理

- **核心结论**：Marketplace 不是列表页，而是能力的目录、信任与生命周期管理层。
- **页面内容**：搜索/分类、适用范围、Owner、版本、权限、依赖、兼容性、质量评分、安装量、弃用状态；发布路径 Draft → Pilot → Stable → Deprecated。
- **讲述重点**：组织内部 Marketplace 的核心价值是减少重复造轮子，同时控制能力扩散风险。
- **不要放**：仿照消费应用商店只展示漂亮卡片。

### 32｜Harness：在任务现场组装正确能力

- **核心结论**：Harness 根据任务、仓库和权限动态装配知识与 Plugin，并持续记录运行证据。
- **页面内容**：Task/Repo Signal → Context Resolver → Policy/Permission → Plugin Selection → Agent Loop → Verification → Trace/Feedback。
- **讲述重点**：Marketplace 负责“有什么”，Harness 负责“这次该加载什么、允许做什么”。
- **不要放**：默认加载所有知识和所有 Plugin。

### 33｜能力晋升与迭代：从一次经验到稳定产品

- **核心结论**：只有经过重复验证、质量评估、Owner 负责和版本治理的经验才应晋升为组织能力。
- **页面内容**：Observe → Capture → Generalize → Evaluate → Package → Pilot → Publish → Monitor → Improve/Deprecate；标出从知识条目到 Skill、再到 Plugin 的晋升条件。
- **讲述重点**：沉淀的目标不是“保存”，而是下一次能够被可靠调用。
- **不要放**：一次项目成功后立刻全组织推广。

## 八、团队规模化落地

### 34｜SDD 的风险：Spec 也会制造确定性幻觉

- **核心结论**：SDD 不能消除不确定性；它只让假设、边界和证据更可见。
- **页面内容**：过早冻结、假精确、Spec 漂移、上下文污染、验证不足、循环失控、工具锁定、责任稀释八类风险。
- **讲述重点**：每个风险都给出一个检测信号，而不是只罗列名词。
- **不要放**：把风险归咎于“员工不会写 Prompt”。

### 35｜SDD 反例：看起来规范，实际不可执行

- **核心结论**：最危险的失败不是没有文档，而是文档存在却不能约束实现和验收。
- **页面内容**：六组 Bad → Better：愿望式 Spec、伪技术细节、线性大 Plan、实现先行后补 Spec、测试替代验收、多套事实源。
- **讲述重点**：每个反例都指向前面某个 Gate 或机制。
- **不要放**：把反例写成空泛口号。

### 36｜团队协作：围绕产物与质量门，而不是聊天记录

- **核心结论**：团队协作的最小单元是有 Owner、有状态、有验收证据的 Artifact。
- **页面内容**：Product/Domain Owner 负责意图与规则；Tech Lead 负责架构与 Plan；Developer/Agent 负责实现与证据；QA/Reviewer 负责独立验证；Platform/Enablement 负责 Harness、Plugin 与度量。
- **讲述重点**：展示 Spec → Plan → Tasks → Code/Evidence → Release 各交接点和批准权。
- **不要放**：把所有角色都变成文档审批人。

### 37｜渐进式落地路线：先闭环，再规模化

- **核心结论**：团队应从一个高价值场景建立最小闭环，而不是一次上线完整 SDD 平台。
- **页面内容**：Stage 1 单 Feature 模板；Stage 2 Review Gate + TDD；Stage 3 Repo 级 Harness；Stage 4 Plugin/Knowledge 复用；Stage 5 Marketplace + Eval + Governance。
- **讲述重点**：每个阶段都列进入条件、成功信号和不应提前建设的能力。
- **不要放**：固定的周数承诺。

### 38｜度量：观察可靠交付，不追逐生成量

- **核心结论**：SDD 的成功指标是更短的可靠交付周期、更少的返工和更高的复用，不是生成代码或 Prompt 数量。
- **页面内容**：Flow（Clarify→Accepted Lead Time）、Quality（验收通过率/逃逸缺陷）、Alignment（Spec 变更与返工）、Agent Reliability（无人工修复完成率/越权拦截）、Reuse（Plugin 使用与复用成功率）。
- **讲述重点**：指标需要趋势和基线；避免单一指标驱动错误行为。
- **不要放**：虚构业务数据。

### 39｜完整系统图：从一次需求到可复用能力

- **核心结论**：可靠 AI 开发是“意图协议 + 执行图 + 反馈循环 + 运行控制 + 组织复用”的共同结果。
- **页面内容**：人类意图 → Explore/Grill → Spec → Plan/Graph → Implement/TDD/Loop → Verify/Reconcile → Release；下层由 Knowledge、Plugin、Marketplace、Harness 支撑；运行证据回流到 Spec 与能力晋升。
- **讲述重点**：逐层回扣前 38 页，最后收束为一句话：“不要只让 Agent 写得更快，要让系统更可靠地知道该写什么、如何证明，以及如何把经验留下来。”
- **不要放**：新增概念或工具。

## 4. 内容边界与合并原则

- **不设置独立章节页**：章节信息通过页眉小标签和章节色体现，不消耗额外页面。
- **Spec、Plan、Implement 脱离工具讲解**：三部分只讲定义、输入输出、质量标准、反例和 Gate。
- **框架位于 TDD 与 Loop 之后**：先建立判断标准，再讨论 OpenSpec、Spec Kit、Superpowers。
- **Grill 位于框架章节开头**：它是进入 Spec 前的澄清机制，不与 SDD 框架混为一类。
- **知识库、Plugin、Marketplace、Harness 不拆成零散技巧**：它们共同组成可复用能力系统。
- **每页一个主结论**：复杂页面可以有多个元素，但所有元素必须服务同一句 takeaway。

## 5. 讲述节奏建议

以 50–60 分钟分享为假设：

- 01–09：10–12 分钟，快速建立问题与全局模型。
- 10–20：18–22 分钟，是方法论主体。
- 21–27：9–11 分钟，用判断标准理解工具。
- 28–33：8–10 分钟，提升到组织能力建设。
- 34–39：7–9 分钟，落地与收束。

如需压缩到 40 分钟，优先合并口头讲述而不删除逻辑节点：04+05、12+13、17+18、30+31、34+35；页面仍可保留，演讲时快速带过。
